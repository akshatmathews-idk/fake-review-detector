04 / DESIGN DECISIONS

Why we made these choices.

Our final pipeline reflects measured trade-offs in validation performance, generalisation behaviour and static-browser deployment—not a claim that one method is universally best.

Text only as input

We used review text as the prediction input. Rating and product category were kept for exploratory and error analysis so the classifier focuses on linguistic patterns and the browser demo only needs text.

Deduplicate before splitting

We removed 22 repeated review-text occurrences before the split. This reduces the chance that identical reviews appear in both training and test data and inflate evaluation.

Stratified 80/20 split

The classes are nearly balanced. Stratification preserves their proportions in both partitions, while a fixed random seed makes the experiment reproducible.

TF–IDF unigrams + bigrams

Unigrams capture individual terms; bigrams capture short phrases. TF–IDF downweights corpus-wide common terms and highlights terms that are more distinctive to a review.

No English stop-word removal

Our experiments performed better without removing English stop words. Common words and short function-word patterns can still carry stylistic information, so we retained them.

Five-fold CV and Macro F1

Stratified five-fold CV gives repeated validation estimates. Macro F1 gives equal weight to OR and CG, rather than allowing performance on one class to dominate the selection metric.

Why compare linear and tree models?

Linear models are efficient with sparse, high-dimensional TF–IDF. Random Forest and XGBoost tested whether non-linear patterns and handcrafted style features added value. They did not outperform the strongest linear models in our experiments.

Why Logistic Regression?

The best LinearSVC CV Macro F1 was slightly higher (about 94.38% vs 93.98%), but its train–validation gap was larger (about 5.27 vs 3.96 percentage points). Logistic Regression also provides native class probabilities, avoiding an extra calibration stage.

Why test vocabulary size?

We tested 5k, 10k, 25k and 50k LinearSVC feature limits to quantify the browser-size trade-off. The 10k version was compact; increasing the limit from 25k to 50k did not improve CV Macro F1.

Why browser inference?

GitHub Pages serves static files, not a Python backend. Exporting the TF–IDF vocabulary, IDF weights, coefficients and intercept lets JavaScript run the selected classifier locally in the browser.

Interpretation and validation caveats

The train–validation gap is a diagnostic, not proof of overfitting. Logistic Regression probabilities are not guaranteed to be calibrated. The existing test split was inspected during development, so external data is needed for a stronger generalisation claim. The model predicts the dataset's labels; it does not establish real-world authorship, fraud or truthfulness.

05 / MODEL SELECTION

Why Logistic Regression is the final model.

LinearSVC achieved a slightly higher CV Macro F1 in the tuned comparison. Logistic Regression had a smaller training–validation gap and naturally provides class probabilities.

09 / LIMITATIONS

What this project cannot establish.

Dataset dependence

Performance may change on reviews from other platforms, products or time periods.

Label validity

Dataset labels may not perfectly represent the real-world distinction between generated and original writing.

Text-only features

TF–IDF captures word and phrase patterns, not deep context, intent, sarcasm or factual accuracy.

Evaluation caveat

The held-out test split was inspected during development; external validation is still needed.

Generative AI assistance was used during development for explanations, code drafting/debugging and documentation support. TEAM CONTRIBUTIONS

Who did what

Akshat MathewsI made the initial file structure and basic outline of the notebooks and python files required for the project. I made the initial notebooks which had basic Linear regression and Linear SVC models to check their performance. The website was made with suggestions from Daksh. AI was used to convert the ideas for the website like the interactive element of being able to input your own reviews and testing them on our model as well as putting the example reviews. We were unable to do any testing related to LLMs because we were short on time.
Daksh RathiI was mainly responsible for analyzing the code and pointing out main flaws which could result in lower accuracies and overfitting. For example, initially I thought that the model should not learn and classify based on words like "and", "or", etc., so we made the model remove words like these. But later we found out that they were critical for learning, so we accordingly tuned the parameters so that the model does not solely depend on generic words. Identifying overfitting was not very hard, but removing it took a lot of effort as we had to change many parameters like the regularization penalty, TF-IDF parameters like min_df, max_df, max_features, etc. Our model has been trained on data that is relatively old, so it might result in very poor accuracies on modern LLM reviews. We could have made it better by adding modern LLM reviews to the training and testing sets to make a better model. Another flaw is that we used only the review texts for classification without considering ratings and categories, which could make our model biased toward certain aspects of reviews.
